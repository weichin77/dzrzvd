======================================================================
1. EXECUTIVE_INTENT
======================================================================

Build a production-grade, read-only integration that periodically retrieves the
kuSport Shopee seller catalog, identifies only DZRZVD products, normalizes the
product records, assigns each product to a Shopee category hierarchy, persists
the resulting catalog in Supabase Postgres, and renders it on the existing
DZRZVD Next.js website hosted by Vercel.

The public website is a discovery and brand-presentation layer. Product purchase
and checkout continue on Shopee. A public visitor request must never make a live
Shopee API request. The website reads cached normalized data from Supabase
Postgres through server-only repository functions.

Confirmed production behavior:
  - Authorized Shopee Open Platform integration.
  - Once-daily synchronization.
  - Default run target: approximately 02:00 Asia/Taipei.
  - Vercel cron expression: 0 18 * * * because Vercel cron uses UTC.
  - Vercel hosts Next.js, Node.js Route Handlers, Cron, environment variables,
    cache revalidation, and runtime logs.
  - Supabase provides managed Postgres and invite-only operator Auth.
  - Supabase is provisioned or connected through Vercel Marketplace.
  - Runtime SQL uses the Supabase transaction pooler.
  - Migrations and controlled maintenance use the non-pooled/direct connection.
  - Supabase Storage, Realtime, Edge Functions, Data API access to app tables,
    and pg_cron are not required.
  - Shopee marketplace category taxonomy is the only grouping mode for this release.
  - DZRZVD matching uses normalized product title/name substring matching for
    "DZRZVD" or "杜戛地".
  - Only products with Shopee status NORMAL and confirmed available stock above
    zero are publicly visible.
  - /products is a category-overview page and /products/[categorySlug] provides
    required separate category pages.
  - Product cards show only the Shopee listing image and a shortened title.
  - Product cards open the corresponding Shopee listing in a new tab.
  - Desktop uses four cards per row; mobile uses two compact cards per row.
  - The visual direction balances editorial brand presentation and e-commerce density.
  - Public copy uses Traditional Chinese with small English brand accents.
  - The only visitor filter dimension is category.
  - The catalog is implemented only in new routes. Existing pages and existing
    shared components must not be modified.
  - A simple protected single-operator admin page provides sync status, manual
    synchronization, and audited product overrides.
  - The last valid database catalog remains public when synchronization fails.
  - Missing products are soft-deactivated only after a complete successful scan.

External production dependency:
  - Shopee must approve the developer application and required API permissions.
  - The kuSport seller account must authorize the application.
  - Production client credentials must be configured in Vercel.
  - A production Supabase project must be connected to Vercel with correctly
    scoped environment variables.
  - Preview and development must use an isolated non-production Supabase project.

3. GOALS
======================================================================

GOAL-001:
  Import every active DZRZVD product that the approved Shopee APIs expose for the
  authorized kuSport shop.

GOAL-002:
  Exclude products from all other brands in the kuSport shop.

GOAL-003:
  Persist stable normalized product records keyed by Shopee item_id.

GOAL-004:
  Map each product to a Shopee marketplace category and a complete category
  breadcrumb.

GOAL-005:
  Render marketplace category overview sections and required separate category
  pages without implementing seller-defined ShopCategory grouping.

GOAL-006:
  Automatically update product title, SKU, brand, price, stock summary, status,
  images, Shopee URL, category, and source update timestamp.

GOAL-007:
  Serve a responsive, accessible, balanced editorial/e-commerce catalog with
  four cards per desktop row, two per mobile row, and image/title-only cards.

GOAL-008:
  Preserve the last valid catalog when Shopee, Vercel cron, or the database write
  workflow encounters a transient failure.

GOAL-009:
  Keep all Shopee credentials, authorization codes, access tokens, refresh
  tokens, partner keys, and signatures out of browser code and logs.

GOAL-010:
  Provide observable synchronization runs and a safe manual recovery path.

5. PRODUCT_AND_TECHNICAL_DECISIONS
======================================================================

DECISION-001:
  question: What does "Shopee product categories" mean?
  confirmed: Shopee marketplace product taxonomy.
  implementation_value: marketplace
  shop_category_mode_implemented: false
  design_requirement:
    - Preserve source taxonomy separately from curated presentation metadata.
    - /products contains overview sections.
    - /products/[categorySlug] is required for separate category pages.

DECISION-002:
  question: How frequently should synchronization run?
  confirmed: Once daily.
  notes:
    - Vercel cron uses UTC.
    - Hobby runs may occur anywhere within the scheduled hour.
    - Vercel cron does not automatically retry failed invocations.

DECISION-003:
  question: How should out-of-stock items be displayed?
  confirmed: Hide from all public catalog queries and pages.
  store_data_regardless_of_display: true
  unknown_stock_visibility: hidden
  required_public_stock_predicate: available_stock greater than zero

DECISION-004:
  question: How are DZRZVD products detected?
  confirmed:
    1: Normalize the Shopee product title/name.
    2: Include when title contains "DZRZVD", compared case-insensitively.
    3: Include when title contains "杜戛地".
    4: Apply an audited operator title-classification include or exclude exception
       when present; it cannot bypass status or stock gates.
  prohibited:
    - Using Shopee brand metadata as an automatic inclusion requirement.
    - Using description, category, or SKU as an automatic inclusion rule.
    - Automatic fuzzy inclusion.
    - Importing the entire kuSport catalog.

DECISION-005:
  question: What application platform and database should be used?
  confirmed:
    hosting_and_compute: Vercel
    database: Supabase Postgres
    operator_authentication: Supabase Auth
    provisioning: Vercel Marketplace when stable for the account
    ORM: Drizzle ORM for application queries
    migration_source_of_truth: supabase/migrations SQL files
  runtime_connection:
    variable: POSTGRES_URL
    mode: Supabase transaction pooler
    prepared_statements: disabled
  migration_connection:
    variable: POSTGRES_URL_NON_POOLING
    use:
      - Supabase CLI migrations
      - database dumps
      - controlled maintenance
  excluded_platform_services:
    - Supabase Storage because Shopee images remain remote
    - Supabase Realtime
    - Supabase Edge Functions
    - Supabase pg_cron because Vercel Cron is the scheduler
    - direct browser access to application tables

DECISION-006:
  question: How should images be served?
  confirmed:
    - Retain authorized Shopee image URLs.
    - Restrict Next.js image remotePatterns to exact observed Shopee CDN hosts.
    - Display listing images as-is without edits, color grading, or local cropping.
    - Use object-fit contain in a stable card image frame.
    - Provide a local branded placeholder.

DECISION-007:
  question: What is the visual direction?
  confirmed: Balanced editorial and e-commerce.

DECISION-008:
  question: What is the product grid density?
  confirmed:
    desktop: four cards per row
    mobile: two compact cards per row

DECISION-009:
  question: What appears on a product card?
  confirmed:

  excluded_from_card:
    - Price.

    - SKU.
    - Category label.
    - Badge.
    - Visible CTA copy.
  interaction:
    - Entire card is one accessible external link.
    - Opens the corresponding Shopee page in a new tab.

DECISION-010:
  question: What filters are available?
  confirmed: Categories only.

DECISION-011:
  question: What public language is used?
  confirmed: Traditional Chinese with small English brand accents.

DECISION-012:
  question: Where does the catalog appear?
  confirmed:
    - Dedicated new catalog routes only.
    - Do not modify home, about, location, header, footer, or other existing pages/components.

DECISION-013:
  question: What operator interface is required?
  confirmed:
    - Simple protected single-operator admin page.

  name: Public storefront crawler
  priority: last_resort
  prerequisites:
    - Shopee API path and authorized upstream alternatives are unavailable.
    - Shopee terms and applicable law have been reviewed.

  constraints:
    - No harvested login cookies.
    - No credential sharing.
    - No bypassing access controls.
    - Low request rate.
    - Strict caching.
    - Exponential backoff.

  limitations:
    - JavaScript-heavy site.
    - Anti-automation measures.
    - UI and internal payload formats can change.
    - Vercel Functions are not ideal for long browser sessions.
  disposition: do not implement for MVP

Token and authorization lifetimes:
  authorization_code:
    validity_minutes: 10
    one_use: true
  access_token:
    validity_hours: 4
    reusable_during_validity: true
  refresh_token:
    validity_days: 30
    one_use: true
    replacement_returned_by_every_successful_refresh: true
  previous_access_token_after_refresh:
    overlap_minutes: approximately_5
  seller_authorization:
    maximum_days: 365
    seller_can_select_shorter_expiry: true
    reauthorization_required_after_expiry: true

Authorization flow:
  1. Administrator requests GET /api/shopee/auth/start.
  2. Server verifies administrator authorization.
  3. Server creates random state with expiry, intended shop/market, and nonce.
  4. Server stores or signs state server-side.
  5. Server redirects to https://open.shopee.com/auth using the verified current
     parameters and auth_type=seller.
  6. Shopee redirects to /api/shopee/auth/callback with code, shop_id, and state.
  7. Callback validates state, expiry, expected redirect, and replay status.
  8. Server calls POST /api/v2/auth/token/get using public endpoint signing.
  9. Server encrypts access and refresh tokens before persistence.
 10. Server calls GET /api/v2/shop/get_shop_info.
 11. Server verifies shop_name identifies the intended kuSport shop, region=TW,
     and status=NORMAL.
 12. Server writes token and authorization expiry audit metadata without storing
     the authorization code.
 13. Server redirects administrator to a non-secret status page.
 14. Administrator initiates a dry-run sync.

Token refresh rules:
  - Refresh when token expiry is less than 10 minutes away.
  - Serialize refresh operations with the serverless-safe shop sync lease and
    a token-row compare-and-swap condition.
  - Refresh only on the server.
  - Call POST /api/v2/auth/access_token/get.
  - Submit partner_id, the latest refresh_token, and shop_id.
  - Atomically replace access token, refresh token, and both expiry timestamps.
  - Never reuse a consumed refresh token.
  - Use compare-and-swap or a database transaction to prevent a stale process
    from overwriting the newest token pair.
  - On an upstream token-expired response, refresh once and replay once.
  - Do not loop indefinitely on authorization failures.
  - On refresh revocation or invalid refresh token:
      authorization_status = revoked_or_error
      catalog = unchanged
      alert = required
      operator_action = reauthorize

    - Authorization state.

    - Authorization audit status.

  SupabaseAuthBoundary:
    - @supabase/ssr cookie clients.

12. DZRZVD_CLASSIFICATION
======================================================================

Reason:
  kuSport is a mixed-brand store. Incorrect automatic inclusion is a catalog and
  brand-integrity defect.

Normalization function:
  input: string
  operations:
    - Unicode normalization, recommended NFKC after validation.
    - Convert full-width forms where appropriate.
    - Trim leading and trailing whitespace.
    - Collapse repeated whitespace.
    - Convert to a comparison case.
    - Normalize punctuation for matching only.
    - Preserve original display text separately.

Configuration:
  title_tokens:
    - DZRZVD
    - 杜戛地
  classification_version:
    - Increment whenever title tokens, normalization, or override semantics change.

Rule order:
  RULE-1:
    if: product_filter_override exists
    result: override decision
    match_method: manual_include or manual_exclude

  RULE-2:
    if: normalized product title contains "DZRZVD" using case-insensitive Latin comparison
    result: include
    match_method: title_alias

  RULE-3:
    if: normalized product title contains "杜戛地"
    result: include
    match_method: title_alias

  RULE-4:
    otherwise: exclude
    match_method: title_not_matched

Safety rules:
  - Do not use Shopee brand, description, category, or SKU to include an item.
  - Never fuzzy-match an item directly into the public catalog.
  - Record classification reason and version.
  - Alert when included catalog count drops or grows by more than 30% compared
    with the previous successful run.
  - Alert when included count is zero.
  - Provide audited title-classification include and exclude controls in the
    protected admin page.
  - Never allow an override to bypass status=NORMAL or confirmed stock above zero.

13. CATEGORY_GROUPING
======================================================================

Marketplace category mode:
  configuration_value: marketplace
  status: confirmed_and_only_mode_for_current_release
  relationship:
    - One product has one Shopee category_id.
    - A category can have one parent.
    - /products renders marketplace category overview sections.
    - /products/[categorySlug] renders a separate page for a visible category.
    - Category is the only visitor filtering dimension.
  path_algorithm:
    1. Start at product.category_id.
    2. Add current display_name.
    3. Follow parent_category_id.
    4. Stop at null or root sentinel.
    5. Reverse collected names.
    6. Reject a repeated category ID as a cycle.
    7. Stop and warn above a safe maximum depth.
  unknown_category_behavior:
    1. Refresh taxonomy once.
    2. Persist product with diagnostic flag if still unresolved.
    3. Place product in a low-priority "Other" category.
    4. Emit warning.

Shop category mode:
  configuration_value: shop-category
  status: not_implemented_in_current_release
  relationship:
    - One product may appear in many seller-defined categories.
    - Persist many-to-many membership.
    - Use shop category status and sort_weight.
  public_behavior:
    - None in the current release.
    - Retain documentation as future research only.

Presentation override rule:
  - Source category identity and hierarchy are immutable integration data.
  - Human-facing label, description, slug, visibility, order, and hero media are
    local presentation data.
  - Never overwrite source category names merely to change the website label.

14. SYNCHRONIZATION_ALGORITHM
======================================================================

FULL_SYNC:
  step_01:
    action: Authenticate trigger.
    cron_requirement:
      Authorization header exactly equals Bearer + CRON_SECRET.
    failure:
      status_code: 401
      no_database_or_shopee_work: true

  step_02:
    action: Create sync_run with status=running.
    capture:
      - trigger
      - mode=full
      - started_at
      - deployment_id

  step_03:
    action: Acquire the app_private.sync_lock row lease keyed by shop_id.
    acquisition:
      - Generate owner_run_id from the current sync_run.
      - Atomically insert the lease or take it only when locked_until is expired.
      - Use database time and a bounded lease duration.
    if_locked:
      sync_status: skipped_locked
      side_effects: none
    rationale:
      - Vercel runtime SQL uses Supavisor transaction pooling.
      - Session advisory locks are unsafe because later statements may use
        different database sessions.

  step_04:
    action: Load shop authorization and ensure token freshness.
    refresh_threshold_minutes: 10
    refresh_atomicity:
      - Hold and heartbeat the shop-level row lease.
      - Use only the latest one-use refresh token.
      - Replace access token, refresh token, and expiries in one transaction.
      - Use a compare-and-swap condition against the encrypted refresh-token
        version or token updated_at value.
      - Never allow a stale process to overwrite the new token pair.

  step_05:
    action: Verify shop and refresh marketplace categories if stale.
    shop_verification:
      endpoint: /api/v2/shop/get_shop_info
      required:
        - intended kuSport shop identity
        - region=TW
        - status=NORMAL
    category_request:
      endpoint: /api/v2/product/get_category
      language: zh-hant
      stale_after_days: 7

  step_06:
    action: Paginate get_item_list for required statuses.
    requirements:
      - Follow next_offset until has_next_page=false.
      - Deduplicate item IDs.
      - Preserve item status and update_time.
      - Detect unexpected pagination loops.

  step_07:
    action: Decide which products need base info.
    full_mode:
      - Fetch NORMAL items unless a safe optimization uses unchanged source update_time.
      - Preserve non-NORMAL item status for audit and public hiding.
    correctness_priority:
      - Favor complete validated details over premature request minimization.

  step_08:
    action: Batch get_item_base_info.
    batch_size_maximum: 50
    lease_rule:
      - Heartbeat sync_lock between successful Shopee batches.
      - Abort safely if the process no longer owns the lease.
    failure_rule:
      - Any irrecoverable batch failure fails full sync.
      - Do not proceed to missing-product inactivation.

  step_09:
    action: Normalize all valid item records.
    validation:
      - ID precision.
      - HTTPS image and product URLs.
      - Decimal prices.
      - Timestamp conversion.
      - Empty optional fields.
      - Status mapping.
      - image.image_url_list[0] as the public listing image.
      - stock_info_v2.summary_info.total_available_stock as the product-level
        public stock gate.

  step_10:
    action: Classify DZRZVD.
    record:
      - is_dzrzvd
      - match_method
      - classification_version
    default_rule:
      - Normalized title contains DZRZVD or 杜戛地.
      - Audited manual title-classification override wins.
      - Override cannot bypass status=NORMAL.
      - Override cannot bypass confirmed available_stock greater than zero.

  step_11:
    action: Resolve category paths.
    unknown_behavior: refresh_once_then_other_group_and_warning

  step_12:
    action: Validate run-level invariants.
    invariants:
      - discovered_count greater than or equal to enriched_count as expected.
      - no duplicate item IDs.
      - every included product has non-empty name.
      - every included product has safe canonical URL.
      - included count anomaly is flagged.
      - public visibility requires NORMAL status, inactive_at null, and confirmed
        available_stock greater than zero.

  step_13:
    action: Begin database transaction.
    writes:
      - Upsert categories.
      - Upsert products.
      - Set last_seen_at to run.started_at for observed items.
      - Preserve first_seen_at on updates.
      - Set inactive_at=null for rediscovered active items.

  step_14:
    action: Mark unseen products inactive.
    precondition:
      - Full enumeration and enrichment completed successfully.
    filter:
      - Same shop.
      - Previously active.
      - last_seen_at older than current run.started_at.
    prohibited:
      - Hard delete.
      - Inactivation after a partial or failed scan.

  step_15:
    action: Complete sync_run in same or subsequent safe transaction.
    fields:
      - status=succeeded
      - finished_at
      - counts
      - warning_count
      - endpoint_request_count
      - Shopee request IDs for failed or warned calls

  step_16:
    action: Update shopee_shop.last_sync_at.

  step_17:
    action: Commit.

  step_18:
    action: Revalidate catalog cache.
    tag: shopee-catalog
    precondition: committed successful write

  step_19:
    action: Release sync_lock in finally only when owner_run_id still matches.

  step_20:
    action: Return safe response.
    include:
      - run_id
      - status
      - summary counts
    exclude:
      - tokens
      - signatures
      - partner key
      - raw upstream body

INCREMENTAL_SYNC:
  use_after:
    - Full sync correctness is proven.
  inputs:
    - Last committed source watermark.
    - update_time_from and update_time_to.
  overlap_minutes: 5
  rules:
    - Never advance watermark before database commit.
    - Repeated items are safe because writes are idempotent.
    - Incremental sync does not replace periodic full reconciliation.
    - Do not infer deletion from absence in an incremental window.

DRY_RUN:
  purpose:
    - Compare API result and classification without changing public records.
  writes_allowed:
    - sync_run and safe diagnostics.
  writes_prohibited:
    - Product visibility changes.
    - Category presentation changes.
    - Cache invalidation.

IDEMPOTENCY_INVARIANTS:
  - item_id is the product write key.
  - Replaying the same upstream payload creates no duplicate product.
  - Replaying category data creates no duplicate category.
  - Marketplace category identity is category_id and parent relationships are
    updated without duplicate rows.
  - Token refresh is serialized.
  - Refresh token replacement is atomic and stale refresh results cannot win.
  - Sync is serialized per shop.
  - Cache invalidation follows commit.

24. RISK_REGISTER
======================================================================

RISK-001:
  priority: P0
  description: Shopee app is not approved or does not receive Product API permission.
  probability: medium
  impact: blocks production API sync
  mitigation:
    - Start approval first.
    - Develop against sanitized fixtures.
    - Use seller CSV as interim source.

RISK-002:
  priority: P0
  description: Title-token classifier imports an unrelated title or misses a DZRZVD title after naming changes.
  probability: medium
  impact: brand and catalog integrity failure
  mitigation:
    - Match only normalized title tokens DZRZVD and 杜戛地.
    - Do not infer from brand, description, SKU, or category.
    - Audited manual include/exclude overrides.
    - Dry-run review.
    - Product count anomaly alerts.

RISK-003:
  priority: P1
  description: Seller authorization expires or is revoked.
  probability: medium
  impact: catalog becomes stale
  mitigation:
    - Refresh early.
    - Alert.
    - Reauthorization runbook.
    - Preserve cached data.

RISK-004:
  priority: P1
  description: Partial sync marks valid products inactive.
  probability: low
  impact: visible product loss
  mitigation:
    - Inactivate unseen products only after complete successful scan.
    - Transactional writes.

RISK-005:
  priority: P1
  description: Shopee response schema changes.
  probability: medium
  impact: validation or normalization failure
  mitigation:
    - Runtime schemas.
    - Tolerate unknown fields.
    - Preserve request IDs.
    - Fixture updates.
    - Fail without corrupting catalog.

RISK-006:
  priority: P1
  description: Secret leakage through logs, response, or client bundle.
  probability: low
  impact: severe
  mitigation:
    - Server-only modules.
    - Redaction.
    - Security tests.
    - Only Supabase URL and publishable key are NEXT_PUBLIC.
    - SUPABASE_SECRET_KEY and database URLs are server-only.
    - Encrypted token storage.

RISK-007:
  priority: P2
  description: Vercel Hobby cron timing is imprecise.
  probability: high
  impact: minor freshness variance
  mitigation:
    - Set freshness expectation to daily.
    - Upgrade only if sub-daily requirement is real.

RISK-008:
  priority: P2
  description: Shopee images fail or host pattern changes.
  probability: medium
  impact: broken product cards
  mitigation:
    - Placeholder.
    - Host monitoring.
    - Exact allowlist.
    - Rights-reviewed copy alternative.

RISK-009:
  priority: P2
  description: Existing encoding or stale tests block clean delivery.
  probability: medium
  impact: build and content quality
  mitigation:
    - Repair baseline first.
    - Establish clean build and tests before feature acceptance.

RISK-010:
  priority: P3
  description: Shopee category labels are poor merchandising labels.
  probability: medium
  impact: user discoverability
  mitigation:
    - Keep source taxonomy.
    - Add local category_presentation overrides.

RISK-011:
  priority: P1
  description: Vercel preview or local deployment is accidentally wired to
    production Supabase.
  probability: medium
  impact: production data mutation or operator-account exposure
  mitigation:
    - Separate Supabase projects and Vercel environment scopes.
    - Startup guard that rejects known production project ref outside production.
    - Destructive integration tests run only on non-production.

RISK-012:
  priority: P1
  description: Runtime code assumes session affinity or prepared statements while
    using Supavisor transaction pooling.
  probability: medium
  impact: intermittent synchronization, locking, or query failure
  mitigation:
    - Prepared statements off.
    - Expiring row lease instead of advisory locks.
    - Short transactions with no external HTTP inside a transaction.
    - Integration tests through POSTGRES_URL.

RISK-013:
  priority: P1
  description: SUPABASE_SECRET_KEY leaks or an app schema is exposed through the
    Supabase Data API.
  probability: low
  impact: authorization bypass and broad database access
  mitigation:
    - Browser uses publishable key only.
    - Server secret key is optional and isolated to audited Auth administration.
    - App schemas are not exposed; anon/authenticated grants are revoked.
    - Bundle, route-response, and database-grant tests.

RISK-014:
  priority: P2
  description: Vercel Marketplace Supabase integration changes during Public Alpha.
  probability: medium
  impact: provisioning or environment synchronization disruption
  mitigation:
    - Treat Marketplace as provisioning convenience, not a runtime dependency.
    - Document manual connection using the same Supabase project and env contract.
    - Pin application package versions and verify env values after integration changes.

RISK-015:
  priority: P1
  description: Database loss cannot be restored within the required window.
  probability: low
  impact: catalog history, overrides, and encrypted Shopee authorization loss
  mitigation:
    - Use paid daily backups and PITR where the recovery objective requires it.
    - On Free, schedule encrypted off-site logical dumps with supabase db dump.
    - Test restore to non-production.
    - Back up encryption-key recovery material separately from database backups.

RISK-016:
  priority: P2
  description: The recommended @supabase/ssr package changes while it remains beta.
  probability: medium
  impact: operator login, callback, or session-refresh regression
  mitigation:
    - Pin the package version.
    - Isolate Supabase client creation and authorization behind small adapters.
    - Test login, callback, cookie refresh, expiry, and logout before upgrades.
    - Review official release notes before changing versions.

26. DEFINITION_OF_DONE
======================================================================

The feature is done only when all of the following are true:
  - Shopee application and seller authorization work in production.
  - Vercel and production Supabase are connected with verified environment scope.
  - Required supabase/migrations are applied from the non-pooled connection.
  - Runtime SQL uses the Supavisor transaction pooler with prepared statements off.
  - Production and non-production Supabase projects are isolated.
  - Full sync is idempotent and failure-safe.
  - Expiring sync row leases prevent overlap and recover after worker loss.
  - DZRZVD classifier is approved against the real kuSport inventory.
  - Marketplace category tree is stored and grouping is correct.
  - /products overview and separate category pages are responsive and accessible.
  - Desktop has four cards per row and mobile has two.
  - Cards show only the original Shopee image and shortened title.
  - Inactive and out-of-stock products do not render.
  - Existing pages and shared components remain unchanged.
  - Images and outbound links are valid.
  - Public rendering does not call Shopee live.
  - Cron and manual routes are protected.
  - Invite-only Supabase Auth, app_admin authorization, the protected admin page,
    and audited overrides work.
  - App schemas are unavailable to browser Data API roles.
  - Tokens are encrypted and redacted.
  - Tests pass.
  - Production build passes.
  - Scheduled production sync succeeds.
  - Environment, migration, sync, reauthorization, and backup/restore runbooks
    exist and have been exercised.
  - Product owner signs off on catalog accuracy.
