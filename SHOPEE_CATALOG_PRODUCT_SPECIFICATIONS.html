01 / North star

Product vision

Make dzrzvd.com.tw the clearest branded way to discover DZRZVD products while keeping Shopee as the transactional destination. The experience should feel curated, current, and trustworthy—not like a generic embedded marketplace feed.

01

Discoverable

Visitors quickly understand which product groups exist and find relevant items.

02

Current

Only active, confirmed in-stock products appear; source status and category placement refresh daily.

03

Branded

The catalog belongs visually to DZRZVD, not to an unstyled data feed.

04

Honest

Visitors know that product details and checkout continue on Shopee.

Product promise “Explore the latest DZRZVD collection by product category, then purchase through the official kuSport Shopee shop.”

02 / Why this exists

Problem statement

Visitor problem

  • The DZRZVD website currently presents broad collections but not a current item-level catalog.
  • The kuSport Shopee shop contains multiple brands, so visitors must distinguish DZRZVD products themselves.
  • Marketplace layouts prioritize commerce breadth, not DZRZVD's brand story or taxonomy.
  • Static links become stale when products or collections change.

Business problem

  • Manual website catalog maintenance duplicates seller work.
  • Brand traffic can leak into unrelated products inside a mixed-brand store.
  • There is no owned catalog surface for category-level SEO and campaign links.
  • There is no reliable view of whether the public brand site reflects the active DZRZVD assortment.

Product hypothesis

If DZRZVD automatically publishes its active Shopee products into a branded, category-organized catalog, visitors will find suitable items with less effort and generate more qualified outbound visits to Shopee, without increasing recurring merchandising work.

03 / Audience

Users and jobs to be done

A

Outdoor apparel shopper

Job: “Help me browse DZRZVD products by type and see what is currently available.”

  • May arrive from search, social media, or a campaign.
  • Needs clear product grouping and visual comparison.
  • Expects every visible card to represent an active, in-stock listing.
B

Brand-aware returning visitor

Job: “Show me what is new or still available from DZRZVD.”

  • Recognizes product codes or styles.
  • Wants a fast path from brand site to Shopee listing.
  • May compare men's, women's, seasonal, or functional categories.
C

Catalog operator

Job: “Keep the public catalog accurate without manually copying every listing.”

  • Needs understandable sync outcomes and safe recovery.
  • Needs to include or exclude an exceptional product.
  • Needs confidence that other kuSport brands will not appear.

Secondary stakeholders

  • Brand/marketing owner reviewing presentation, labels, and campaigns.
  • Developer maintaining the Shopee integration and deployment.
  • Search engines consuming server-rendered category content.
  • Shopee as the external source and transaction platform.

Default entry behavior

  • Only active products with confirmed available stock greater than zero appear.
  • Selected category is encoded in a required category URL.

Screen B — Mobile catalog

商品系列

Mobile requirements

  • Exactly two compact product cards per row at mobile breakpoints.
  • Category-only controls horizontally scroll without trapping the page, or use an accessible select.
  • Touch targets are at least 44×44 CSS pixels where practical.
  • Each card visibly contains only the original Shopee image and shortened title.

  • Keep the full category navigation accessible.
  • Provide a clear way back to all products.
  • Use a stable local slug independent of future Shopee label changes.
  • If the category is hidden or invalid, return a deliberate 404 rather than an empty successful page.

09 / Core component

Product card specification

Visible content — exactly two elements

  • Original primary Shopee listing image, or local placeholder only when it fails.
  • Product title visually shortened to two lines.

Do not display

  • Current price or original price.
  • Stock or availability label.
  • Seller SKU/style code.
  • Category name or filter metadata.
  • New, discount, promotion, or other badges.
  • A separate visible Shopee CTA.

Card behavior

Interaction requirements

  • A restrained hover/focus treatment may lift the card or shift the image, matching the balanced visual direction.
  • The whole card has one visible keyboard focus state.
  • There are no nested links or secondary controls inside the card.
  • The Shopee/new-tab destination is announced through the accessible label because no visible CTA is shown.
  • Track the click once, without delaying navigation materially.

11 / Operations product

Operator experience

The MVP includes a simple protected single-operator page at /admin/shopee-catalog. It is a new route and does not modify any existing public page.

MVP operator capabilities

  • Connect or reconnect the kuSport Shopee shop.
  • Trigger a dry-run synchronization.
  • Trigger a full synchronization.
  • See latest run ID, start/end time, outcome, and summary counts.
  • See safe warnings such as unknown categories or count anomalies.
  • Search a product by item ID or title and see its title-token match result.
  • Force include or exclude a product with a required audit reason.
  • Confirm last successful public catalog update.

Minimum run summary

42Items discovered
18DZRZVD included
24Other brands excluded
0Warnings

Admin authorization requirements

  • Use Supabase Auth with one operator invited or created through the Supabase Dashboard; do not expose public sign-up.
  • Use @supabase/ssr cookie-based sessions and verify each protected request with server-side auth.getUser().
  • Require the verified Auth UUID to have an active app_private.app_admin record; authentication alone is not authorization.
  • No custom password hash, application session secret, or parallel local account store is required.
  • Manual sync and override actions require both a valid Auth session and active administrator authorization.
  • Rate-limit login attempts and protect mutating actions against CSRF.
  • Actions store the verified Auth user UUID, reason, and time.
  • No administrative response displays Supabase secret keys, database URLs, Shopee tokens, partner keys, or signatures.

13 / Inclusive design

Accessibility requirements

  • Meet WCAG 2.2 AA where applicable to the implemented catalog.
  • Provide one descriptive page h1 and ordered section headings.
  • All category controls and whole-card product links are keyboard operable.
  • Visible focus is not removed and has adequate contrast.
  • Product images have meaningful alt text; decorative imagery uses empty alt text.
  • Out-of-stock and inactive products are absent rather than represented through color.
  • Text and interactive controls meet color contrast requirements.
  • Touch targets are sufficiently large and separated.
  • Reduced-motion preference disables nonessential animation.
  • Client-side result updates, if used, provide an accessible announcement.
  • Horizontal category scrolling does not prevent keyboard or page navigation.
  • Whole-card outbound links communicate through their accessible name that Shopee opens in a new tab.

Accessibility test set

  • Keyboard-only navigation from header through category controls and product cards.
  • Screen-reader heading and link-list review.
  • 200% browser zoom without content loss.
  • Mobile portrait layout and large text settings.
  • Automated axe or equivalent checks plus manual review.

15 / Discovery quality

SEO and performance specifications

SEO

  • Catalog and category headings render on the server.
  • /products has a unique title, description, canonical URL, and social metadata.
  • Category pages have stable local slugs and unique metadata when enabled.
  • Avoid thin local product-detail pages that simply duplicate Shopee.
  • Use descriptive internal links from home and relevant brand content.
  • Do not index empty or hidden category pages.
  • Make the Shopee transaction relationship transparent.

Performance targets

≤ 2.5s Target LCP

75th percentile on representative mobile traffic.

≤ 0.1 Target CLS

Stable image ratios and reserved content space.

≤ 200ms Target INP

Minimal client JavaScript and simple filters.

Performance implementation rules

  • No live Shopee calls in the visitor rendering path.
  • Use server-rendered cached catalog queries.
  • Optimize images with responsive sizes and lazy loading.
  • Prioritize only above-the-fold imagery when justified.
  • Keep category filtering server-side or use a small client component.
  • Avoid shipping raw Shopee payloads to the browser.

18 / Product sign-off

Acceptance criteria

Catalog accuracy

  • Product owner reviews the real synchronized assortment.
  • All expected active, in-stock titles containing DZRZVD or 杜戛地 appear.
  • Title-unmatched, inactive, and out-of-stock products do not appear.
  • Category placement is understandable and traceable.
  • Images, active/in-stock eligibility, and links match representative Shopee listings.

Visitor experience

  • /products presents category overview sections.
  • Every visible category has a separate category page.
  • Category is the only filter dimension.
  • Desktop shows four cards per row and mobile shows two compact cards per row.
  • Each card visibly shows only the original Shopee image and shortened title.
  • The whole card opens the correct Shopee page in a new tab.
  • Empty, missing-image, and stale states are intentional.

Trust and resilience

  • Last-updated time is visible.
  • A failed sync leaves the last valid catalog online.
  • Partial sync failure does not remove products.
  • No raw operational error reaches visitors.
  • The site accurately represents Shopee as purchase destination.
  • No existing page or existing shared component is modified.

Operations

  • Production Vercel is connected to production Supabase in the selected nearby regions.
  • Preview and development use separate non-production Supabase resources.
  • Runtime pooling and non-pooled migration paths are both verified.
  • Scheduled synchronization succeeds in production.
  • Manual dry run and full retry are tested.
  • Invite-only Supabase Auth protects the admin page and active administrator allowlist.
  • Force include/exclude actions require and retain an audit reason.
  • Browser Data API roles cannot access application schemas.
  • A non-production backup restore succeeds.
  • Sync anomalies are observable.
  • Reauthorization procedure is documented.

19 / Launch

Release and validation plan

  1. Platform provisioning: connect Vercel to production Supabase, create separate non-production resources, choose nearby regions, and verify environment scopes.
  2. Schema and Auth: apply supabase/migrations, verify schema grants, invite the operator, and create the active app_admin record.
  3. Fixture preview: build the UI against sanitized representative Shopee payloads on non-production Supabase.
  4. Authorized dry run: fetch real kuSport data without changing public catalog visibility.
  5. Catalog comparison: compare title-token matches, active/in-stock exclusions, categories, images, and links.
  6. Product-owner review: approve the two title tokens, category presentation, product set, and hidden out-of-stock behavior.
  7. Preview deployment: test mobile, desktop, accessibility, performance, Auth expiry, lease recovery, and error states.
  8. Recovery drill: restore a backup into isolated non-production and confirm the migration chain and key-recovery procedure.
  9. Initial production sync: populate Supabase while the dedicated routes remain unshared if necessary.
  10. Soft launch: expose catalog URL directly and run production smoke tests.
  11. Dedicated-route launch: publish /products and category URLs without changing existing pages or navigation.
  12. Monitor 72 hours: watch sync success, item counts, database latency, images, clicks, and runtime errors.
  13. Post-launch review: document baseline metrics and prioritize version 1.3.

Launch blockers

  • Shopee authorization or required API permission is unavailable.
  • Taiwan developer screening, callback-domain configuration, or live Shop/Product/Public permissions are incomplete.
  • Production Vercel is not connected to the intended production Supabase project, or preview/local environments can reach it.
  • POSTGRES_URL runtime pooling and POSTGRES_URL_NON_POOLING migration access are not separately verified.
  • Supabase Auth allows public sign-up, the operator lacks an active app_admin record, or server-side identity verification is absent.
  • Browser roles can query catalog or app_private, or SUPABASE_SECRET_KEY reaches a client bundle.
  • The authoritative Supabase migration chain does not apply cleanly, or backup restore has not been tested.
  • Sync overlap protection depends on session advisory locks instead of the expiring row lease.
  • The real product set contains unresolved false positives.
  • Tokens or partner credentials appear in logs or browser artifacts.
  • Partial failure can remove existing public products.
  • The project does not build or critical tests fail.
  • Product owner decisions encoded in this document are not implemented exactly.

Serverless synchronization lease

  • app_private.sync_lock stores shop_id, owner_run_id, acquisition time, heartbeat time, and locked_until.
  • Acquisition is one atomic insert-or-update that succeeds only when no lease exists or the prior lease is expired according to database time.
  • The worker heartbeats between Shopee batches, aborts if ownership is lost, and releases only when both shop and owner IDs match.
  • Token refresh remains serialized under the lease and uses compare-and-swap so an old worker cannot overwrite the newest one-use refresh token.
  • No database transaction remains open while waiting for Shopee HTTP responses.

Platform security and recovery contract

  • Only NEXT_PUBLIC_SUPABASE_URL and NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY enter browser configuration.
  • SUPABASE_SECRET_KEY, pooled and non-pooled database URLs, Shopee secrets, and CRON_SECRET remain server-only.
  • Prefer Supabase publishable and secret keys for new work; do not build new dependencies on legacy anon/service_role key names.
  • Use paid scheduled backups and PITR when the recovery objective requires them; on Free, create regular encrypted off-site logical dumps.
  • Test restore in non-production and recover the Shopee token-encryption key separately because database backups do not contain Vercel environment secrets.

Conditional and excluded interfaces

  • v2.product.get_model_list is conditional and not used in MVP unless aggregate product stock is missing or inconsistent.
  • ShopCategory APIs are not used because the confirmed grouping source is Shopee marketplace taxonomy.
  • Product, price, stock, order, buyer, logistics, and marketing write operations are excluded.
  • Push notifications may become a faster change signal, but cannot replace daily full reconciliation.
  • Undocumented Shopee web endpoints and browser scraping are excluded.
