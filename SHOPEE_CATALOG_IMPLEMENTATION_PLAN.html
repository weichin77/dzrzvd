01 / Outcome

Executive summary

Build an authorized, read-only Shopee catalog integration. A protected server-side job will fetch the kuSport product inventory, retain only DZRZVD products, attach each product to Shopee's category hierarchy, save normalized records in Supabase Postgres, and revalidate a public product catalog in the existing Next.js application on Vercel.

Daily Default synchronization

Approximately 02:00 Asia/Taipei on Vercel Hobby.

API-first Source of truth

Shopee Open Platform, not scraped storefront HTML.

Cached Failure behavior

Supabase retains the last valid catalog during Shopee outages.

Read-only Permission scope

No listing, price, stock, order, or shop mutations.

External gate Implementation can start with fixtures, but production synchronization depends on Shopee developer approval, appropriate API permissions, and authorization of the kuSport seller account. The current authorization guide was verified on 2026-07-29 and is marked by Shopee as updated on 2026-07-24.
Confirmed platform Vercel hosts Next.js, Route Handlers, scheduled synchronization, environment variables, cache revalidation, and runtime logs. Supabase supplies managed PostgreSQL and invite-only Supabase Auth for the protected operator. Shopee images remain on Shopee; Supabase Storage, Realtime, Edge Functions, and pg_cron are not required.

06 / Official integration

Shopee Open Platform design

Documentation verification This contract was checked against Shopee's official Open Platform pages on 2026-07-29. The API calls guide is marked updated 2025-11-21; the newer Authorization and Authentication guide is marked updated 2026-07-24.

Application and authorization

  1. Create an appropriate Shopee Open Platform application for an in-house/custom seller integration.
  2. Complete Taiwan developer screening and request only the necessary product, shop, and public/auth permissions; do not request ShopCategory scope for this release.
  3. Register www.dzrzvd.com.tw as the production callback domain and use https://www.dzrzvd.com.tw/api/shopee/auth/callback as the callback URL.
  4. Generate the current authorization URL at https://open.shopee.com/auth with partner_id, auth_type=seller, redirect_uri, response_type=code, and a cryptographically random state.
  5. Validate callback state, then accept the returned one-use code and shop_id.
  6. Exchange the code through POST /api/v2/auth/token/get; persist the access token and refresh token encrypted.
  7. Call GET /api/v2/shop/get_shop_info and verify the intended kuSport shop, region TW, and shop status NORMAL.
  8. Record token expiry, authorization expiry, shop status, authorization time, and last refresh result.

Authentication characteristics Shop API calls require partner_id, current Unix timestamp, sign, access_token, and shop_id. The request timestamp expires after five minutes. The shop-level signature is the lowercase hex HMAC-SHA256 of partner_id + api_path + timestamp + access_token + shop_id, keyed by the partner key. Public token endpoints use the endpoint-appropriate public base string partner_id + api_path + timestamp.
Current token and authorization rules The callback code is one-use and expires after 10 minutes. Access tokens last four hours. Refresh tokens last 30 days, are one-use, and every successful refresh returns a replacement refresh token that must be stored atomically. The previous access token remains valid for approximately five minutes after refresh. Seller authorization can last up to 365 days and must be renewed after its selected expiry.

Shopee's July 2026 guide introduces the fixed /auth URL but still contains legacy signed /api/v2/shop/auth_partner examples and a conflicting note elsewhere on the same page. Implement and test the new /auth flow in Sandbox; retain no dependency on the legacy authorization endpoint.

HTTP client rules

  • Use the Singapore/global production host https://partner.shopeemobile.com unless Shopee assigns a different regional host.
  • Set explicit connect, response, and overall operation timeouts.
  • Retry only transient network failures, HTTP 429, and retryable 5xx responses.
  • Use exponential backoff with jitter and a strict retry budget.
  • Do not retry invalid signatures, authorization errors, or invalid parameters without correction.
  • Capture response request_id, endpoint, duration, attempt count, and error category.
  • Treat a non-empty Shopee response error as a failed call even when the HTTP response is 200.
  • Start with a small concurrency limit of two to four requests and tune only against approved application quotas.
  • Redact access tokens, refresh tokens, partner key, signatures, and authorization codes from logs.

Runtime components

  • Next.js Route Handlers for auth, callbacks, cron, and protected manual sync.
  • Node.js runtime for crypto, database access, and Shopee calls.
  • Server Components for catalog reads and category pages.
  • Small Client Components only for category controls or the protected admin interface.
  • Supabase Postgres provisioned or connected through Vercel Marketplace.
  • Supabase Auth with @supabase/ssr for cookie-based operator sessions.

Reliability boundaries

  • Shopee failures never block normal public page requests.
  • The synchronization job is the only routine writer.
  • Database state changes happen transactionally after validation.
  • A full scan marks missing products inactive only when the scan completes.
  • Rendering consumes normalized data, never raw Shopee payloads.

Vercel and Supabase topology

  • Place the Supabase project and Vercel Functions in the closest matching region; the preferred production target is Singapore, with Vercel region sin1, subject to current plan availability.
  • Use the Supabase transaction pooler connection injected as POSTGRES_URL for Vercel runtime queries. Configure the SQL driver with prepared statements disabled because transaction mode does not support them.
  • Use POSTGRES_URL_NON_POOLING only for migrations, controlled maintenance, dumps, and restore tooling—not normal Vercel requests.
  • Scope Vercel environment variables independently for Development, Preview, and Production. Preview deployments must not write to the production Supabase project.
  • Use a separate non-production Supabase project by default; Supabase Branching may be adopted later when the selected plan supports it.
  • Keep catalog reads and writes server-side. The browser uses Supabase only for the operator authentication session.
Marketplace integration maturity Supabase documents its Vercel Marketplace integration as Public Alpha as of this revision. Use it for automatic provisioning and environment synchronization when stable for the account; otherwise connect an existing Supabase project and configure the same environment variables manually without changing the architecture.

Data lifecycle

  1. Authorize: connect the seller shop and persist encrypted credentials.
  2. Discover: fetch all applicable item IDs and status records.
  3. Enrich: batch-fetch item details and refresh taxonomy when required.
  4. Classify: evaluate DZRZVD match rules and resolve category breadcrumbs.
  5. Commit: upsert valid normalized records inside a transaction.
  6. Publish: invalidate the catalog cache after a successful commit.
  7. Observe: record counts, timings, request IDs, warnings, and errors.

Supporting tables

  • sync_run: run ID, trigger, mode, timestamps, outcome, counts, latency, error summary, deployment ID.
  • sync_request: optional per-endpoint request audit with Shopee request ID and redacted error fields.
  • product_filter_override: item ID, title-classification include/exclude decision, reason, operator, timestamps. It cannot bypass the hard NORMAL and stock-above-zero public gates.
  • category_presentation: category ID, custom label, description, order, visibility, optional hero image.

  • shop_category and shop_category_item are researched future tables and must not be created in this release.

Migration and backup policy

  • Keep every schema, index, grant, RLS setting, trigger, function, and seed change in versioned supabase/migrations/*.sql.
  • Apply migrations through a controlled Supabase CLI or CI job using the non-pooled connection; never mutate production schema ad hoc in Table Editor or SQL Editor.
  • Test migrations locally with supabase db reset, then use supabase db push in the release workflow.
  • On paid Supabase plans, verify daily backups and choose PITR when the recovery objective requires it. On Free, schedule and retain off-site logical dumps with supabase db dump.
  • Test restoration before launch and after material schema changes. A database backup restores catalog and integration records, but Vercel environment secrets require a separate recovery procedure.
Retention recommendation Keep normalized product history indefinitely unless policy changes. Retain raw Shopee payloads only when necessary for debugging, remove unexpected personal data, and apply a short retention window such as 30 days.

09 / Processing

Synchronization algorithm

Full reconciliation

  1. Authenticate the request using CRON_SECRET or protected admin authorization.
  2. Create a sync_run row in running state.
  3. Atomically acquire an expiring sync_lock lease keyed to the Shopee shop ID; exit cleanly if another unexpired owner exists.
  4. Load shop credentials and refresh the access token when less than 10 minutes remain.
  5. Rotate access and refresh tokens atomically under the shop row lease with a compare-and-swap update; never reuse a consumed refresh token.
  6. Call shop information on initial authorization and periodically; stop publication if the shop is not the intended TW/NORMAL shop.
  7. Refresh category taxonomy with language=zh-hant when older than seven days.
  8. Fetch item pages for all statuses required to detect active, unlisted, banned, reviewing, seller-deleted, and Shopee-deleted listings.
  9. Deduplicate item IDs and batch-fetch base information for NORMAL items in groups of at most 50.
  10. Validate payload shape and normalize numeric, text, date, image, stock, and category fields.
  11. Apply DZRZVD title classification and audited overrides, then enforce the non-overridable NORMAL and confirmed-stock-above-zero public gates.
  12. Validate referential integrity: every displayed product must have a known or explicitly “Uncategorized” category path.
  13. Within one transaction, upsert categories and products and update last_seen_at.
  14. Only after a successful complete scan, mark previously active but unseen products inactive.
  15. Complete sync_run with counts and timing; update shopee_shop.last_sync_at.
  16. Invalidate the product catalog cache with revalidateTag or revalidatePath.
  17. Heartbeat the lease between long Shopee batches and release it by matching owner_run_id in a finally block.
async function synchronizeShop(trigger, mode = "full") {
  authorizeTrigger();
  const run = await beginRun(trigger, mode);

  return withShopSyncLease(shopId, run.id, async () => {
    const token = await ensureFreshAccessToken(shopId);
    const categories = await ensureFreshCategoryTree(token);
    const itemRefs = await listAllRelevantItems(token);
    const normalItemRefs = itemRefs.filter((item) => item.item_status === "NORMAL");
    const details = await getItemDetailsInBatches(token, normalItemRefs, 50);
    const normalized = details.map(normalizeShopeeProduct);
    const classified = normalized.map(applyDzrzvdRules);

    await db.transaction(async (tx) => {
      await upsertCategories(tx, categories);
      await upsertProducts(tx, classified, run.startedAt);
      if (mode === "full") await markUnseenProductsInactive(tx, run.startedAt);
      await completeRun(tx, run, classified);
    });

    revalidateTag("shopee-catalog");
  });
}

Incremental synchronization

After the full path is proven, use update_time_from and update_time_to to reduce routine API volume. Include an overlap window (for example, five minutes) and retain the daily or weekly full reconciliation as the correctness mechanism.

  • Never advance the incremental watermark before the transaction commits.
  • Use Shopee's source timestamp, not Vercel invocation time, for the watermark.
  • Overlapping windows are safe because upserts are idempotent.
  • A partial batch failure must fail the run and must not mark unseen products inactive.

Idempotency invariants

  • item_id is the product idempotency key.
  • A repeated payload produces no duplicate rows or duplicate category memberships.
  • Token refresh is serialized per shop.
  • The latest refresh token is replaced using compare-and-swap or a transaction before the lock is released.
  • Only one active sync may operate for a shop at a time.
  • Cache invalidation occurs only after successful committed writes.

10 / Brand safety

DZRZVD matching and exclusion logic

The kuSport shop is mixed-brand. The confirmed business rule is title-based: an item is classified as DZRZVD when its normalized Shopee product title/name contains DZRZVD or 杜戛地. An item is never included solely because it belongs to the kuSport shop.

1

Normalize title

Apply Unicode normalization, collapse whitespace, and compare Latin text case-insensitively.

2

Match two tokens

Include when the normalized title contains DZRZVD or 杜戛地.

3

Apply override

An audited title-classification include/exclude exception wins, but cannot bypass active-status or confirmed-stock gates.

Confirmed classifier

# Classification only; public status and stock gates run afterward.
if override(item_id) exists:
  return override decision

title = normalize(item_name)

if title contains_case_insensitive("DZRZVD"):
  include("title_alias")
else if title contains("杜戛地"):
  include("title_alias")
else:
  exclude("title_not_matched")

Configuration and quality controls

  • Keep the two confirmed title tokens in versioned server-side classification configuration.
  • Normalize Unicode, width variants, whitespace, punctuation, and case before matching.
  • Do not infer DZRZVD from Shopee brand, description, category, SKU, or fuzzy similarity.
  • Measure title-matched, override-included, override-excluded, and unmatched counts on every run.
  • Alert when the included count changes by a configurable percentage, such as 30%.
  • Retain match_method so every public product can be traced to a rule.

11 / Information architecture

Category grouping behavior

Marketplace taxonomy — confirmed

Use product.category_id and product.get_category to reconstruct a breadcrumb from leaf category to root.

  • Stable and consistent with Shopee's product classification.
  • Supports overview sections on /products and separate category pages.
  • A product belongs to one marketplace category.

Custom shop categories — not implemented

Use ShopCategory APIs to mirror seller-defined storefront collections and their product membership.

  • Retained in this document only as a researched future alternative.
  • No ShopCategory API calls, tables, filters, or UI switch are included.
  • Changing taxonomy later requires a separate product decision.

Unknown category handling

  1. Attempt an immediate taxonomy refresh once.
  2. If still unknown, persist the product with a diagnostic flag.
  3. Place it in a non-prominent “Other” group rather than dropping it.
  4. Raise an operational warning for manual review.

  • Show cached products with a subtle “last updated” message when a sync is delayed.

Image behavior

  • Allowlist only the exact Shopee CDN host patterns observed in approved API responses.
  • Use Shopee listing images as-is, without local editing, color treatment, cropping, or replacement.
  • Use next/image with object-fit: contain, responsive sizes, lazy loading below the fold, and useful alt text.
  • Use a local branded placeholder when an image fails.
  • Avoid proxying or copying images unless content-use rights and Shopee terms permit it.

SEO and accessibility

  • Server-render category headings and product names for crawlability.
  • Use one page-level h1, followed by logical category h2 headings.
  • Add collection metadata and canonical URLs for DZRZVD pages.
  • Give each linked card an accessible label that includes the full title and announces that Shopee opens in a new tab.
  • Use visible keyboard focus and sufficient contrast.
  • Do not represent dzrzvd.com.tw as the seller of record if checkout occurs on Shopee.

Simple protected admin page

  • Add /admin/shopee-catalog as a new route; do not reuse or modify an existing public page.
  • Use Supabase Auth with @supabase/ssr, secure HttpOnly cookie sessions, and no public signup.
  • Create or invite the one operator through Supabase Dashboard; authorize the session only when its Supabase user UUID has an active app_private.app_admin row.
  • Validate the user server-side with supabase.auth.getUser() on every protected page, Route Handler, and mutation; never trust browser state alone.
  • Show authorization status, last successful sync, latest run outcome, counts, and safe warnings.
  • Provide dry-run and full-sync actions with confirmation and progress/result feedback.
  • Provide audited title-classification include/exclude overrides with a required reason; no override can publish an inactive or out-of-stock item.
  • Never expose tokens, partner key, signatures, raw payloads, or database credentials.

13 / Automation

Scheduling, concurrency, and recovery

Initial Vercel Cron configuration

{
  "$schema": "https://openapi.vercel.sh/vercel.json",
  "regions": ["sin1"],
  "crons": [
    {
      "path": "/api/cron/shopee-sync",
      "schedule": "0 18 * * *"
    }
  ]
}

Vercel cron expressions are UTC. 0 18 * * * targets approximately 02:00 the following day in Taiwan. On Hobby, jobs may execute at any point in the selected hour and cannot run more than once per day. Pro allows more frequent schedules. Configure Supabase in the closest matching region; Vercel Functions otherwise default to iad1, which adds avoidable database latency.

Protected invocation

  • Set a random CRON_SECRET of at least 32 bytes.
  • Require exact Authorization: Bearer ${CRON_SECRET}.
  • Reject missing or mismatched secrets with HTTP 401 before database or Shopee work.
  • Return a compact run ID and outcome, never secrets or complete upstream payloads.

Failure and retry policy

FailureAutomatic behaviorOperator action
Network timeout / 5xxUp to three attempts with exponential backoff and jitter.Retry manually if the run remains failed.
HTTP 429 / rate limitHonor retry guidance when present; slow subsequent batches.Review call volume and API quotas.
Expired access tokenRefresh once, then replay the failed API call once.Reauthorize if refresh fails.
Revoked authorizationStop without altering catalog state.Run seller authorization again.
Partial item-detail failureFail run; do not mark unseen products inactive.Retry from protected admin action.
Database unavailableAbort before cache invalidation.Check Supabase and Vercel status, pooler health, and runtime logs.
Overlapping jobExit as skipped_locked.No action unless lock is stale.
Vercel Cron does not retry failed invocations The application must implement bounded upstream retries and provide a protected manual recovery path. Cached catalog data remains the public fallback.

14 / Protection

Security and privacy controls

Secrets

  • SHOPEE_PARTNER_ID and partner key remain server-only.
  • Only the Supabase URL and publishable key may use NEXT_PUBLIC_; database URLs, Supabase secret key, Shopee secrets, and encryption keys remain server-only.
  • Tokens are encrypted at the application layer before database persistence.
  • Use separate production, preview, and local credentials.
  • Rotate Shopee, Supabase, database, and encryption secrets through documented runbooks.

Authorization

  • Use signed, expiring authorization state to prevent callback forgery.
  • Use the current https://open.shopee.com/auth seller flow and configure the exact production callback domain in Shopee Console.
  • Restrict auth-start and manual-sync routes to a validated Supabase Auth user present and active in app_private.app_admin.
  • Disable public Supabase Auth signup; create or invite the operator administratively.
  • Request read-only scopes and avoid order/buyer data.
  • Reject callback host or redirect mismatches.
  • Rotate the one-use refresh token atomically and alert before its 30-day expiry or the seller authorization expiry.
  • Record authorization and revocation events without storing secret values.

Application security

  • Validate every Shopee response with runtime schemas.
  • Escape all text through React rendering; never inject Shopee HTML.
  • Constrain outbound hosts to official Shopee endpoints.
  • Use parameterized ORM queries.
  • Apply rate limits to manual/admin endpoints.
  • Keep application tables outside exposed Data API schemas and revoke anon/authenticated grants.
  • Never instantiate a Supabase client with SUPABASE_SECRET_KEY in browser code; the secret key bypasses RLS.

Privacy and compliance

  • Do not request or store buyers, orders, addresses, payments, or messages.
  • Document source data, purpose, retention, and deletion behavior.
  • Review Shopee API and image-use terms before launch.
  • Provide a process to remove a listing from the public catalog quickly.
  • Keep raw payload retention limited and monitored.

15 / Operations

Observability and runbooks

Structured log fields

event, run_id, trigger, mode, shop_id, endpoint, request_id, duration_ms, attempt, status, error_code, item_count, and deployment metadata.

Metrics and alerts

Sync health

  • Last successful sync age.
  • Duration and API request count.
  • Consecutive failures.
  • Token refresh failures.

Catalog health

  • DZRZVD product count.
  • New, changed, and inactive counts.
  • Unknown categories.
  • Missing images or prices.

Anomaly thresholds

  • No success for 30 hours.
  • Product count falls by 30%.
  • Zero DZRZVD products.
  • Three consecutive upstream failures.

Operator runbooks

  • Manual sync: invoke the protected route, capture run ID, watch runtime logs, verify the catalog timestamp.
  • Reauthorization: pause sync, start seller authorization, verify shop ID, run a dry run, resume schedule.
  • Bad catalog rollback: disable publishing or restore prior normalized snapshot; do not delete source records blindly.
  • Brand false positive: add force-exclude override, run incremental sync, verify removal, then improve the rule.
  • Unknown category: refresh taxonomy, inspect the category ID, add presentation data if needed, rerun publishing.

Mandatory failure tests

  • An expired access token refreshes once and the original call succeeds.
  • An invalid refresh token leaves the current catalog unchanged.
  • A page-two API failure does not mark products missing or inactive.
  • A repeated full sync does not create duplicate products or categories.
  • A concurrent sync is skipped by the unexpired database lease, and only its owning run can heartbeat or release it.
  • A title containing neither DZRZVD nor 杜戛地 is excluded by default.
  • Titles containing either confirmed token are included regardless of the optional Shopee brand field.
  • Products with zero or unknown available stock are absent from all public catalog queries.
  • A malicious product title renders as text, not executable markup.

Existing-page preservation boundary

Implementation must not edit app/page.tsx, app/about/page.tsx, app/location/page.tsx, app/components/Header.tsx, or app/components/Footer.tsx. Catalog styles must be scoped to the new routes so existing pages remain visually and behaviorally unchanged.

Implementation conventions

  • Keep API transport types separate from normalized domain types.
  • Use runtime schemas at the network boundary.
  • Keep all Shopee signing and token code server-only.
  • Use repository functions instead of direct database queries in React components.
  • Use postgres and drizzle-orm/postgres-js from server modules; initialize runtime SQL with prepare: false for the Supabase transaction pooler.
  • Use supabase/migrations as the only migration history; do not maintain a second independent Drizzle migration chain.
  • Use @supabase/ssr clients for Auth and validate protected requests with a server-side user lookup plus the app_admin allowlist.
  • Place UI copy and category presentation overrides outside transport code.
  • Do not commit production IDs, tokens, partner keys, database URLs, or raw payload dumps.

20 / Completion

Acceptance criteria and definition of done

Functional

  • Authorized kuSport shop can complete an initial full sync.
  • All active, in-stock products whose titles contain DZRZVD or 杜戛地 are imported exactly once unless explicitly overridden.
  • Title-unmatched, inactive, and out-of-stock products are excluded from public queries.
  • Products are grouped by Shopee marketplace taxonomy.
  • Status, price, stock, image, and category changes propagate.
  • Unlisted, reviewing, banned, deleted, and zero/unknown-stock items never render publicly.
  • Each image-and-shortened-title card opens its valid Shopee listing in a new tab.

Reliability and security

  • Repeated syncs are idempotent.
  • Partial failures preserve the last valid catalog.
  • Concurrent syncs cannot overlap.
  • Tokens refresh without browser involvement.
  • All secrets remain server-only and redacted.
  • Cron and manual routes reject unauthorized calls.
  • Supabase Auth public signup is disabled and only active app_admin users can reach operator functions.
  • Runtime SQL uses the Supabase transaction pooler with prepared statements disabled; migrations use the non-pooled connection.
  • Preview and production use separate Supabase data environments.
  • Backup and restore procedures are documented and exercised.
  • Cached catalog renders when Shopee is unavailable.

User experience

  • Catalog works at mobile, tablet, and desktop widths.
  • Desktop uses four cards per row and mobile uses two compact cards per row.
  • /products presents category overview sections and each category has a separate page.
  • Keyboard and screen-reader navigation is coherent.
  • Missing images and empty categories have intentional states.
  • Last-updated information is visible and understandable.
  • The balanced editorial/e-commerce design uses Traditional Chinese with small English accents.
  • No existing page or shared existing component is modified.

Operations

  • Production cron is visible in Vercel and has succeeded.
  • The protected simple admin page shows sync status and supports audited product overrides.
  • Manual retry and reauthorization runbooks are tested.
  • Sync health and catalog-count anomalies are observable.
  • Database migration and rollback procedures are documented.
  • Product owner approves the imported catalog set.
